# Hero Armor — інженерний хаб (Burning Man 2026)

Меморіальна інсталяція памʼяті Захара Захарова — https://hero-armor.com/
Вартовий промовляє його голосом. Цей репозиторій — інженерна частина:
дані, моделі, розрахунки, дашборд → https://hero-armor.github.io/

## Словник (щоб слова не означали дві речі)

| Термін | Що це |
|---|---|
| **Система** | велика частина проєкту: аудіо, світло, живлення, броня |
| **Деталь** | залізка/запчастина — позиція в закупівлі (`bom.json`) |
| **Лабораторія** | набір **експериментів** однієї системи |
| **Експеримент** | один розрахунок потрібного параметра |

Ієрархія: **система → лабораторія (експерименти) + сторінка → деталі**.
Раніше все звалося «компонент» — і велика частина, і залізка; тепер розведено.

## Правило №1 — правда живе в `data/`

Правиш JSON → перезбираєш → публікуєш. **Руками в HTML і `knowledge/` — нічого.**

```bash
cd site && python3 build.py --docs   # дашборд + OKF-бандл + docs/
python3 site/guard.py                # перевірка перед публікацією
```

Числа рахують тільки моделі (`*/model/*.py`). Системи розділені за принципом
«споживач не знає про джерело»: `lights` і `audio` рахують власне споживання,
`solar` імпортує його з них. Тому цифри не розходяться: змінив режим світла —
баланс живлення переїхав сам.

## Приватне vs публічне

**Приватне = вся робота. Публічне = тільки вирішене.**
Обговорення, чернетки, невирішене, сирий збір із чатів, голоси, переписка,
адреси, трек-номери → приватний репозиторій `Hero-Armor/private` і
`data/private/` (gitignored). У цей публічний репозиторій потрапляє лише
ПРИЙНЯТЕ рішення — оформлене в `data/*.json`. Сумнів → у приватне.

## Структура

```
data/        спільна база: systems, bom, tasks, orders, decisions, addresses, project
audio/       модель + схема + params/cases системи звуку
lights/      модель + схема + params/cases системи світла (чистий споживач)
solar/       живлення: станція + масив; тягне споживання з lights і audio
armor/       так само, коли зʼявиться контент
site/        збірник сайту, шаблони, guard.py
knowledge/   OKF-бандл — ГЕНЕРУЄТЬСЯ з data/, не правити руками
docs/        генерований сайт (збирає CI)
```

`knowledge/` — [OKF v0.2](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf):
один markdown-концепт на файл, YAML frontmatter, крос-лінки = граф. Читати
можна будь-чим (GitHub, Obsidian, агент), правити — тільки JSON.

## Життєвий цикл системи

Реєстр — `data/systems.json`; статуси `concept → in-design → design-ready → build`.

1. **Реєстрація** — картка в `systems.json` → сторінка генерується сама.
2. **Дані** — запис у спільних `data/*.json` з `"system": "<key>"` сам
   потрапляє на сторінку, дашборд і в `knowledge/`. Креслення — `site/assets/`
   + `figures` у картці.
3. **Інженерія** — `<key>/data/params.json` + `<key>/model/*.py`.
4. **Своя лабораторія** — шаблон `site/templates/<key>.tmpl.html` + секція в
   `build.py`, інтерактив окремою сторінкою.

Повний плейбук — [knowledge/playbooks/](knowledge/playbooks/index.md).

## Хто вирішує

Єдиного «головного» немає — кожен головний у своїй зоні. Ліза — команда й
фінанси, Володимир (конструктор) — конструкція й креслення, Іван — електрика.
У кожному рішенні стоїть `decided_by` + зона, тож в одній темі видно, хто що
вирішив.

## Покупки

Агенти ГОТУЮТЬ замовлення (лінки, ціни, статуси) — **купує тільки людина**.
Після покупки: запис в `orders.json`, статус деталі → `have`, rebuild.
Куди слати — вирішує Іван; `addresses.json` лише підказує за `move_date`.
